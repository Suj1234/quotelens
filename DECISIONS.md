- **2026-09-23 · Supabase API keys (P0-T2, checked supabase.com/docs/guides/api/api-keys).** Legacy `anon`/`service_role` JWT keys are deprecated by end of 2026; new keys are `sb_publishable_…` / `sb_secret_…`. A secret key works in `createClient` exactly like service_role and bypasses RLS; Supabase rejects it from browsers (User-Agent check). We keep the TRD env names — `SUPABASE_SERVICE_ROLE_KEY` may hold either the legacy service_role JWT or an `sb_secret_` key.
- **2026-09-23 · Supabase Storage API (P0-T2).** Docs pages for the JS reference moved (404); verified against installed `@supabase/storage-js@2.117.1` typings: `storage.from(bucket).createSignedUrl(path, expiresInSeconds, { download?, transform? })` → `{ data: { signedUrl } }`; `upload(path, body, { contentType, upsert })`; `createBucket(id, { public })`. Signed URLs use 3600 s (TRD §5: 60 min).
- **2026-09-23 · Migrations.** `0001_init.sql` / `0002_views.sql` are extracted **verbatim** from TRD §6.1–6.21 (awk over the code blocks). Additions, each marked in the file: (a) no `create extension pgcrypto` — `gen_random_uuid()` is core since PG13; (b) RLS enabled on every table with no policies + privileges revoked from `anon`/`authenticated`, so a leaked anon/publishable key reads nothing (service role bypasses RLS, so the app is unaffected); (c) views set `security_invoker = true`; (d) `run_readonly_query` gets `search_path = public`, execute revoked from public/anon/authenticated and granted to `service_role` (TRD §6.21 asks for this). (e) `0003_storage.sql` creates the four private buckets via `storage.buckets` (idempotent). Validated locally on PGlite (embedded PG): all apply; read-only function blocks writes even mid-transaction. Applied via **`npm run db:migrate`** (`scripts/migrate.ts`, `postgres` dev dependency, Session pooler `DATABASE_URL`; each file once, tracked in `public._migrations`, RLS on). No Supabase MCP or psql in this session. The script parses the URL by hand because DB passwords may contain `/ ? # @` and it never logs the URL. `npm run db:check` verifies.

The SQL guard (P4-T1) must allow only the `v_*` views. Upgrade path if needed: a dedicated `query_reader` role granted SELECT on views only, and the function owned by it.
